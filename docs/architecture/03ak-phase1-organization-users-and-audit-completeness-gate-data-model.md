## 0. Summary

1. **Organization model (Spec §78).** Four new tenant-scoped tables and one stub: `departments` and `designations` (R4 masters), `employees` (the Spec §06 Employee entity, carrying the direct-manager chain), `project_role_grants` (per-project Site Head / Project Head assignment), and a deliberately minimal `projects` stub. `roles` gains a `grant_scope` semantic column; `user_roles` gains a constant column that pins it to tenant-scope roles.
2. **NI-17 is fixed without touching `user_roles`' primary key.** Project roles live in their own append-only grant table. The PO's Employee D example is stored exactly, and no per-project cardinality is imposed (AI-Q-2 stays open).
3. **AC-55 is expressible.** "Management authority requires BOTH reporting hierarchy AND project-level authorization" is one SQL query over `employees` and `project_role_grants`. It keys on permissions, never on role names. The test suite runs it against the PO's example (§4.7).
4. **Builder-Side Admin is an R2 role row**, `builder_side_admin`. It is the only default holder of `audit.read`, `audit.export`, `audit.correct` and `audit.retract`. `owner` and `admin` lose `audit.read` (§5).
5. **AGX-10 is resolved without superseding R6's storage guarantee** (`ARCH`, §6.4). Nothing in `audit_events` is ever updated or deleted, by any role; a trigger now enforces this for every role, including the table owner. The PO's "edit or delete" (ACG-3/ACG-4) becomes an appended supersession record. The record carries a mandatory reason (ACG-7) and the administrator's identity (ACG-6). A database trigger checks that the actor holds the permission (ACG-4).
6. **The four built `audit_events` collisions** named in 03ag §7.5 and 03ah are each resolved (§6.1). This covers `ON DELETE CASCADE`, `tenant_id NOT NULL` versus pre-auth events, the missing before/after convention, and the missing categories.
7. **A live Phase 0 cross-tenant leak was found and closed** (§7). `crm_app` could read every tenant's audit rows, and forge rows, by naming an `audit_events_YYYY_MM` partition directly. The partitions had no RLS of their own, and `crm_app` held direct grants on them. It was confirmed empirically before the fix, and a regression test now covers it.
8. **Tests.** There are 83 new tests: 55 organization, 19 audit, and 9 schema-conformance (the R1/R4 CI lint that the Phase 0 note §13 asked for first). All pass, and the 43 Phase 0 tests still pass unchanged.

Every item inside that scope is either `PO LOCKED` or an `ARCH` mechanism that serves a locked rule without changing it. Items that would *change* a locked rule are not built. ## 3. Migration layout and how it was generated

| File | Produced by | Contents |
|---|---|---|
| `meta/0001_snapshot.json` | `drizzle-kit generate` against the **Phase 0 portion** of `schema.ts`, written to a throwaway folder and committed as the snapshot for migration 0001 | The diff **baseline**: what 0000+0001 already built, as drizzle sees it. Without it, drizzle-kit would diff against nothing and emit `CREATE TABLE tenants/users/…` again |
| `0002_phase1_keys.sql` | `drizzle-kit generate` | `roles.grant_scope` with its CHECK and `UNIQUE (tenant_id, id, grant_scope)`. `audit_events UNIQUE (tenant_id, id, occurred_at)` |
| `0003_phase1_org_users_audit_gate.sql` | `drizzle-kit generate` | Every Phase 1 table, index, FK, CHECK and `tenant_isolation` policy (plus `ENABLE ROW LEVEL SECURITY`). The `audit_events` and `user_roles` alterations |
| `0004_phase1_rls_force_triggers_seed_grants.sql` | `drizzle-kit generate --custom`, body written by hand | Only what the Drizzle DSL cannot express: `FORCE ROW LEVEL SECURITY`; partition RLS (§7); triggers; the replaced provisioning functions; the backfill; `crm_app` grants; comments |

**Why two generated migrations rather than one.** In a single run, drizzle-kit 0.30 emits foreign keys that reference *altered* tables before it emits the UNIQUE constraints added to those tables. Three composite FKs target new UNIQUE constraints: `project_role_grants_role_scope_fk` and `user_roles_role_scope_fk` → `roles(tenant_id, id, grant_scope)`, and `audit_events_supersedes_fk` → `audit_events(tenant_id, id, occurred_at)`. A single run therefore produced a migration that fails to apply. The keys were generated first (0002) and everything else second (0003), so no generated SQL was hand-edited or reordered. Future migrations that add a UNIQUE to an existing table and an FK to it must follow the same two-step procedure.

**Constraint names on Phase 0 tables.** Every Phase 0 constraint that Phase 1 references or changes is declared in `schema.ts` under its real PostgreSQL name (`audit_events_tenant_id_fkey`, `audit_events_actor_type_check`, `audit_events_event_category_check`, `users_tenant_id_id_key`, …). This makes a generated DROP/ADD target the real object.

**Verification.** All five migrations were applied in order with `psql -v ON_ERROR_STOP=1` to (a) an empty database and (b) the existing test database (`crm_phase0`, 2 live tenants, backed up first). Both applied cleanly. `drizzle-kit generate` afterwards reports *"No schema changes"*. The `db:migrate` runner is not the application path: 0000 has no statement breakpoints and was applied by `psql` in Phase 0. That is unchanged. 0004 carries breakpoints so it stays runner-compatible.

## 4. Organization model

### 4.1 Shape

```
tenants ─┬─ departments (R4)      ◄──┐
         ├─ designations (R4)     ◄──┤ RESTRICT
         ├─ users ◄── employees ─────┘   employees.reports_to_employee_id ──► employees  (direct manager)
         ├─ roles (grant_scope)             ▲
         │     ▲            ▲               │
         │  user_roles   project_role_grants ── projects (stub)
         │  (tenant roles) (project roles, append-only)
         └─ audit_events (§6)
```

Three independent structures, exactly as 03ai "How to read" separates them. None is derived from another:

| Structure | Table(s) | Answers | Source |
|---|---|---|---|
| Designation | `employees.designation_id` → `designations` | "What is this person's HR title?" | `PO-AI1` ("designation GM"), `PO-AI1·7` |
| Reporting tree | `employees.reports_to_employee_id` | "Whose team is this?" (management **breadth**) | `PO-AF1·B.1`–`·B.5`; AC-55; AG-Q-3 |
| Project role grants | `project_role_grants` | "Who is Site Head / Project Head **on this project**?" (project **authorization**) | `PO-AI1·1`–`·5` |

### 4.2 R4 masters: `departments`, `designations`

Both copy the Phase 0 master shape field for field (0000 §5): `code`, `label`, `description`, `sort_order`, `is_active`, `is_system`, `custom_attributes`, timestamps, `UNIQUE (tenant_id, code)`, `UNIQUE (tenant_id, id)`, the partial picker index and the code-format CHECK.

| | `departments` | `designations` |
|---|---|---|
| Why a master | AG-Q-3-n (PO LOCKED) names the departments. AG-Q-3's replacement rule needs "the relevant department". R4: tenant vocabulary is rows | `PO-AI1` names a designation ("GM"). The titles vary per builder (03ai §3.2, chunk 272). R4 |
| Seeded | **Yes**: `sales`/Sales, `crm`/CRM, `accounts`/Accounts, `marketing`/Marketing, `is_system = true` (AG-Q-3-n verbatim) | **No.** No designation list is locked, and a seeded `is_system` row would be undeletable |
| Semantic columns | None needed yet | **None, on purpose.** A designation confers no authority (`PO-AI1·7`; 03ai R-AI-5). There is no rank or level column for anything to branch on |
| Open question respected | AG-Q-11(f) (where Sales Support / Helpdesk sit) is answered by the tenant adding rows. The schema is neutral | — |

### 4.3 `employees` — why a table, not columns on `users`

The brief suggested extending `users`. **Spec §06 overrides that suggestion.** It lists **Employee** ("Builder-side organizational identity and employment record. Employee history must survive role changes.") as a canonical entity distinct from **User** ("Authenticated system identity"). §78 lists "users, employees" separately. Merging them would be a canonical-entity change, which Spec §88 says Claude must ask about. Keeping them separate also fits three things:

- CP users (Phase 4) will be users and never employees.
- Access ends on `users.status` while the organizational record persists (Spec §57).
- HR-shaped columns stay off the authentication table (0000 `users` comment: "Nothing the AUTH path reads may live here").

| Column | Why | Source |
|---|---|---|
| `id`, `tenant_id` | R1; `UNIQUE (tenant_id, id)` for composite FKs | R1 |
| `user_id NOT NULL`, `UNIQUE (tenant_id, user_id)`, FK → `users` RESTRICT | Every employee in scope is someone the system must authorize; 1:1. `ARCH` J-3: relaxing to nullable later is a one-line change, and the reverse is not | Spec §06, §57 |
| `department_id` → `departments` RESTRICT, nullable | Department membership (AG-Q-3 "active user in the relevant department"). One per employee is `ARCH` J-4 | AG-Q-3, AG-Q-3-n |
| `designation_id` → `designations` RESTRICT, nullable | HR title | `PO-AI1` |
| `reports_to_employee_id` → `employees` RESTRICT, nullable | The **direct** manager. Indirect managers are the transitive chain above. Singular, because the PO's text is singular ("immediate manager"). NULL = top of a tree | `PO-AF1·B.1`–`·B.5`; AC-55 |
| `custom_attributes` | Core entity | R5 |
| `created_at`, `updated_at` (+ trigger) | Convention | 0000 §0.2 |

**Integrity.** The `employees_not_own_manager` CHECK stops self-reference. The `employees_reporting_tree_acyclic` trigger walks the chain upward and refuses any cycle. A per-tenant advisory lock serializes concurrent reporting-line edits, so two transactions cannot each add half of a cycle. Rows are never deleted by the application. Every FK into `employees` is RESTRICT.

### 4.4 `roles.grant_scope` and the scope-pinning FKs

`grant_scope` is `'tenant'` or `'project'`. It follows R2's own pattern, "capabilities are columns on the role, not names": it is to *where a role may be granted* what `requires_2fa` is to 2FA. Two constant columns turn it into a declarative guarantee:

- `user_roles.role_grant_scope` (always `'tenant'`), with FK `(tenant_id, role_id, role_grant_scope)` → `roles(tenant_id, id, grant_scope)`;
- `project_role_grants.role_grant_scope` (always `'project'`), with the same shape of FK.

**Consequences.** A Site Head can never be granted tenant-wide. That is 03ai's R-AI-1, "D becomes Site Head everywhere". A tenant-wide role can never be granted per project. A role's scope cannot be flipped while grants exist (FK `ON UPDATE NO ACTION`). The column is a closed, product-owned vocabulary that authorization reads, so it is a CHECK-constrained typed column, not an R4 master. This is the architecture note §9.3 rule: "It affects auth, authorisation, billing, or isolation → a real, typed column with constraints". Existing `user_roles` inserts are unaffected, because the column defaults.

### 4.5 `project_role_grants` — per-project role assignment (fixes NI-17)

**Why a new table instead of rewriting `user_roles`** (`ARCH` J-5). 03ai §8.1 suggested one grant table with a scope column. Here the Phase 0 `user_roles` keeps tenant-wide grants, and project grants get their own table:

- changing `user_roles`' `PRIMARY KEY (user_id, role_id)` is AD-01 §L.3's "most dangerous migration";
- the Phase 0 permission middleware and every Phase 0 test read `user_roles` as-is;
- Region scope (Spec §08) has no entity yet to reference.

The cost is that permission resolution becomes a union over two tables (§4.7). When Region scope arrives, it gets its own grant table or a generalization of this one. That decision needs the Region entity first.

| Column | Why | Source |
|---|---|---|
| `employee_id` → `employees` RESTRICT | Roles are "assigned … to employees" | `PO-AI1·2` |
| `role_id` + `role_grant_scope` → `roles` RESTRICT | Only `grant_scope = 'project'` roles (§4.4) | `PO-AI1·1` |
| `project_id` → `projects` RESTRICT | "for specific projects" | `PO-AI1·2` |
| `granted_by_user_id`, `granted_at` | Who and when. Grants are admin actions (ACG-1; NI-20) | Spec §08; ACG-1 |
| `revoked_at`, `revoked_by_user_id` | Revocation is a stamp, not a delete | Spec §08 "Role changes must not destroy historical ownership information" |
| *(no `custom_attributes`)* | A relationship, not an entity | R5 governance |

**Constraints — and the ones deliberately absent.**

| Present | Absent, deliberately |
|---|---|
| `UNIQUE (tenant_id, employee_id, role_id, project_id) WHERE revoked_at IS NULL`. This is identity (no duplicate live grant), not cardinality | **Any per-project maximum.** There is no "one Site Head per project" and no "one Project Head per project" (AI-Q-2 is OPEN; AC-51-e′ and GC-31 point to more than one). A maximum can be added later as a partial unique index without restructuring; removing one later would need a data decision |
| `revoked_at >= granted_at`; a revoker implies a revocation | **Any ban on holding both roles.** Project E is legal (`PO-AI1·3`) |
| Trigger `project_role_grants_append_only`: only the one-time revocation stamp may change; a grant cannot be re-pointed or reopened | **A minimum of one Site Head** (LC-23). It is pending PO confirmation, and it can only be enforced at "project becomes operational", which is a Phase 2 lifecycle that does not exist yet (§9) |
| `crm_app` has no DELETE | **Reason columns.** 03ai §8.1 recommends one (`ARCH`, not approved). The grant and revoke audit events carry it under ACG-2 |

**The PO's example, stored.** The test fixture holds exactly: D Site Head on B, D Project Head on C, A Site Head on C, D Site Head on D, D Project Head and Site Head on E. It also adds a second Site Head and a second Project Head on C, to prove the absence of a cardinality limit (P1-G-1, P1-G-2).

### 4.6 `projects` — a deliberate minimal stub

Columns: `id`, `tenant_id`, `name`, `custom_attributes`, `created_at`, `updated_at`, plus `UNIQUE (tenant_id, id)`. The table exists only as the FK target for `project_role_grants`. Spec §82: *"Do not artificially delay required foundational entities simply because their broader module is later."* Phase 2 (§79 Project / Tower / Floor / Inventory / Pricing) **adds columns to this table; it does not replace it.**

**Two deviations from the brief's column list, both rule-driven:**

- **`custom_attributes` is present.** R5 makes it mandatory on core business entities *in the DDL that creates the table*, and Project is a canonical entity (Spec §06).
- **`status` is absent.** The brief listed it, but also required that "no column should exist that you can't point to a locked decision or an engineering rule for". No project lifecycle is locked. R4 forbids a CHECK-constrained status column. An R4 `project_statuses` master is Phase 2's to design. A status column would therefore either violate R4 or pre-empt Phase 2. The 1:1 rule wins over the column list.

### 4.7 AC-55 — expressible, and expressed through permissions

AC-55 and AG-Q-3: *"Management authority requires BOTH reporting hierarchy AND project-level authorization."* 03ai §8.2 splits it into gates. The schema answers all of them in one query. The version below is the one the test suite runs (P1-A55):

```sql
-- May :actor perform the management act guarded by permission :perm
-- over :target on :project?
WITH RECURSIVE above_target AS (
  SELECT e.reports_to_employee_id AS manager_id FROM employees e WHERE e.id = :target
  UNION ALL
  SELECT e.reports_to_employee_id FROM above_target a JOIN employees e ON e.id = a.manager_id
  WHERE a.manager_id IS NOT NULL
)
SELECT
  EXISTS (                                   -- gates 1+2: capability, scoped to the project
    SELECT 1 FROM project_role_grants g
    JOIN role_permissions rp ON rp.tenant_id = g.tenant_id AND rp.role_id = g.role_id
    JOIN permissions p       ON p.tenant_id  = rp.tenant_id AND p.id = rp.permission_id
    WHERE g.employee_id = :actor AND g.project_id = :project
      AND g.revoked_at IS NULL AND p.key = :perm)
  AND EXISTS (SELECT 1 FROM above_target WHERE manager_id = :actor)  -- gate 3: reporting tree
  AS allowed;
```

Results on the PO's example, with a Rep who reports to D:

| Case | Result |
|---|---|
| D (Project Head on C and the Rep's direct manager) manages the Rep on C | **allowed** |
| A (Site Head on C, but the Rep is outside A's tree) | **denied** — 03ai LC-22's stated consequence |
| The CEO (indirect manager, no grant on C) | **denied** — "project assignment does not independently expand…", and the converse holds too |
| D on Project F (designation GM, no grant) | **denied** — `PO-AI1·7` |
| The Rep over D | **denied** — direction follows the tree |

**Nothing keys on a role name.** The capability gate joins through `role_permissions` to a permission key. Site Head and Project Head are only default holders (R2; 03ai §8.2 item 3). Project acts (03ai §3.5 rows 1–7) use gates 1+2 alone. The application check itself is **not** written. Nothing exists to authorize until Phase 3/5 builds the acts, and each act's permission is added with it.

### 4.8 Builder-Side Admin — an R2 role, not a flag

`builder_side_admin` ("Builder-Side Admin") is a system role row: `is_system = true`, `grant_scope = 'tenant'`, `requires_2fa = true`.

- **Name and meaning:** AG-Q-3 and the AG-Q-3-m rename, "the builder tenant's administrative authority, held by the CEO or an authorized executive".
- **2FA:** the architecture note §6.2 DECIDED rule, which makes 2FA mandatory for executive roles.

Its identity is its permissions, so no logic, database or application, compares a role key or name. The supersession guard (§6.4) checks `audit.correct` / `audit.retract`. AG-Q-3's *"CRM staff may receive delegated setup/configuration permissions but do not automatically become Builder-Side Admin"* is honoured by the seed: no other role receives any `audit.*` permission (§5).

**Requirement carried to the role-management endpoints (not built; NI-20, AG-Q-3).** Once `roles.manage` has endpoints, they must refuse privilege escalation:

Without these rules, an `owner` holding `roles.manage` could add `audit.export` to their own role and defeat ACG-9. With them, only a Builder-Side Admin can create another Builder-Side-Admin-equivalent, which matches "the CEO or an authorized executive". **Bootstrap:** tenant signup must assign `builder_side_admin` to the founding user alongside `owner`. Signup is not built.

## 6. Audit Completeness Gate — `audit_events`

### 6.1 The built collisions, each resolved

| Collision (03ag §7.5 / 03ah) | Resolution | Where |
|---|---|---|
| **ACG-8 vs `tenant_id … ON DELETE CASCADE`**: deleting a tenant row deleted its audit history | FK changed to **ON DELETE RESTRICT**, same name. A tenant with audit history cannot be hard-deleted until a Legal/Compliance-validated closure procedure exists (Spec §56; Q15) | 0003; §6.6 |
| **ACG-1 (security events) vs `tenant_id NOT NULL`** | `tenant_id` **stays NOT NULL**; see §6.2 | §6.2 |
| **ACG-2 vs no structured before/after** | `before_state jsonb`, `after_state jsonb` | §6.3 |
| **ACG-1 vs `event_category`** (no security or audit-administration category) | Adds `'security'` and `'audit'`. Adds `actor_type` `'anonymous'` | §6.2; ACG-INV-1 |
| **ACG-3/ACG-4 vs R6 grants (AGX-10)** | Supersession by appended record. Storage stays immutable | §6.4 |

### 6.2 ACG-1: pre-authentication security events (`tenant_id` stays NOT NULL)

**The tension.** 03ag and 03ah flagged that a failed login "for an unknown user" has no tenant. Two options existed:

- **Make `tenant_id` nullable**, with a CHECK allowing NULL only for security events. **Rejected.** It breaks R1's "no exceptions". A NULL-tenant row also fails the `WITH CHECK (tenant_id = app_current_tenant_id())` policy, so `crm_app` could not even insert one without a policy change. That is an RLS-model change (Spec §88: must ask). And under the existing policy nobody could read it.
- **Route by what is actually known.** **Chosen** (`ARCH` J-8). Tenant routing resolves the subdomain to a tenant *before* authentication (architecture note §4.1). A failed login on `company.bmexa…` therefore has a tenant, just no authenticated actor. It is recorded in that tenant's log as `event_category = 'security'`, `actor_type = 'anonymous'`, `actor_user_id` NULL (or the targeted user, if the identifier matched one). The login path sets tenant context from the subdomain, exactly as for any request.

**What remains tenantless**: requests to an unknown subdomain, and unresolvable tokens. These belong to no tenant's audit trail. They are **platform security telemetry**: structured logs and alerting under Spec §73, outside the tenant schema. This follows the precedent of the audit archive manifest (architecture note §8.3: "a manifest of cross-tenant partitions has no meaningful tenant_id, and inventing one would mean carving the first exception into R1"). No table is built for them (§9).

### 6.3 ACG-2: before-and-after values

There are two nullable `jsonb` objects, each CHECKed to be a JSON object when present.

- **What they hold.** Each holds only the changed fields, frozen at write time. R6 still applies: never re-join live tables to render history.
- **"Wherever applicable".** NULL means not applicable, for example on a login.
- **Why two columns rather than one diff** (`ARCH` J-9). "Old → new" renders without diff semantics. A correction's `after_state` is exactly "the corrected values", which ACG-6 requires. Each side can be redacted independently.
- **Sensitive fields.** AD-G-7 makes free-text reassignment reasons sensitive in *audit before/after values and audit export* (03ag SEC-5). Redaction or encryption of such fields is the emitter's responsibility and is **DEFERRED** to the phase that introduces reassignment (Phase 3). Nothing sensitive is written today.

### 6.4 ACG-3 / ACG-4 / ACG-6 / ACG-7 — the AGX-10 resolution (`ARCH`)

> **Label.** This mechanism is the architect's technical resolution of a named contradiction (AGX-10). **The PO decided the business rule, not the mechanism.** The rule is that the Builder-Side Admin may effect an edit or deletion, with a reason and a separate immutable record. The mechanism is to append a superseding record rather than UPDATE or DELETE the original.

**The contradiction.** R6: "never updated and never deleted"; `UPDATE`/`DELETE` are revoked. ACG-3: "immutable for ordinary users, but authorized administrators may edit or delete them". ACG-4: only the Builder-Side Admin.

**The resolution.**

1. **R6's storage guarantee stays whole, and is made stronger.** No role, including the Builder-Side Admin, is ever granted `UPDATE` or `DELETE`. The new `audit_events_append_only` trigger rejects UPDATE and DELETE for *every* role, including the table owner. So the guarantee no longer rests on out-of-band grants alone. The R6 grants (`SELECT, INSERT` only) are also re-asserted in the migration.
2. **"Edit" = a `correction` record; "delete" = a `retraction` record.** Each is a new `audit_events` row with `event_category = 'audit'`. It carries `supersedes_event_id` and `supersedes_occurred_at`, which form a composite same-tenant self-FK to the target. It also carries `supersession_kind` and a mandatory `supersession_reason`.
3. **Presentation follows the chain.** An event whose latest supersession is a retraction is shown as deleted; a correction, as edited, with its `after_state`. "Latest" means `occurred_at`, then `recorded_at`, then `id`. The original row is never touched, and a test asserts it is byte-identical afterwards (P1-ACG-3a).
4. **Why the same table rather than a side table.** A correction *is* an audit event: an administrator action, which ACG-1 requires to be logged. In the same table it inherits append-only enforcement, partitioning, RLS, indexes, export and retention for free. A side table would be a second immutable store to protect, and a second export path to keep complete.

**Enforcement of each locked limb.**

| Locked text | Enforced by |
|---|---|
| ACG-4 "Only the Builder-Side Admin may edit or delete" | Trigger `audit_events_supersession_guard` checks the actor. At insert time they must be an **active** user holding `audit.correct` (correction) or `audit.retract` (retraction) through a tenant-wide role grant. It checks **permission keys**, never a role name (R2) |
| ACG-6 "a separate immutable record" | The supersession is a new row, covered by the append-only trigger. The guard also refuses to supersede a supersession record, even for the Builder-Side Admin. A mistaken correction is fixed by superseding the original again |
| ACG-6 "administrator identity" | CHECK `audit_events_supersession_actor_identified`: `actor_type = 'user'`, `actor_user_id` and `actor_label` (frozen) NOT NULL |
| ACG-6 "timestamp" | `occurred_at` / `recorded_at` |
| ACG-6 "reason for the change" / ACG-7 "must provide a reason before every … edit or deletion" | CHECK `audit_events_supersession_reason_required`: NOT NULL and not blank |
| ACG-6 "details of the edit or deletion" | `after_state` (required for a correction by CHECK `audit_events_correction_has_after_state`), `before_state`, `payload` |
| Target integrity | Composite FK `(tenant_id, supersedes_event_id, supersedes_occurred_at)`. A cross-tenant target is impossible, and the guard reports it (P1-ACG-4c) |

**What this answers of ACG-INV-6.** Three questions are answered:

- "Mechanism … without granting UPDATE/DELETE to crm_app (AD-G-18)": the supersession record above.
- "Whether ACG-6's details include the pre-change content": yes. The original is retained verbatim, so ACG-2's before-values are never lost. The **retention consequence**, that a "deleted" record's data still exists, is exactly NI-9 and is surfaced for the PO (J-1).
- "Immutability of ACG-6 records even against the Builder-Side Admin": yes.

Two questions stay open: multiple Builder-Side Admins (nothing prevents or requires it) and edits to records of the admin's own actions (not restricted; OPEN).

### 6.5 ACG-5: visibility

- **Builder-Side Admin (full).** Seeded `audit.read`, held by `builder_side_admin` alone (§5).
- **"Authorized management users, limited to their respective management scopes."** Not built, and **DEFERRED (Phase 3)**, deliberately. Scoped audit visibility needs a write-time scope anchor on each row (03ag SEC-8, NI-12). R6 forbids re-joining live tables, so the anchor must be captured when the event is written. What that anchor is depends on business objects that do not exist yet: the customer's project and the handler at event time. It also depends on open questions ("scope at event time vs view time", AG-Q-18, V-10).
- **Why deferring forecloses nothing.** Adding a nullable column to a partitioned table is a catalog-only change in PostgreSQL 11+. Phase 3 can add `scope_project_id` / `scope_employee_id` at no cost, alongside the events that populate them. The query shape it will need already exists (§4.7).

### 6.6 ACG-8: indefinite retention

- The tenant FK is **RESTRICT** (§6.1), and there is **no** automatic-deletion path in the schema: no TTL, no cascade, no DEFAULT partition.
- `UPDATE`/`DELETE` are refused by trigger. The supersession FK is `ON DELETE RESTRICT`, and the append-only trigger means it is never exercised.
- **No partition-management or archival job is built.** Spec §87 item 9: "do not implement premature partitioning".

**Reconciling R6's "12 months hot, then archive to S3 and drop"** (`ARCH` J-10). ACG-8 forbids *automatic expiration or age-based deletion*. An archive job that moves an aging partition to S3 and drops it from PostgreSQL does not delete history *only if* the archive remains retained indefinitely and retrievable. ACG-5 and ACG-9 then need a path to cold records (03ag ACG-INV-8). Until the PO confirms that cold archive counts as retention, **no drop of an audit partition is permitted.** Any future archive job must be designed against ACG-8, not only against R6's original text.

**The runway obligation still stands.** Partitions exist through 2027-09. Partition *creation* must be running before then, or audit inserts, and with them every emitting write, fail (0000 §6). Any partition that job creates must also get the §7 RLS treatment. The conformance test (P1-C-1) fails if it does not.

### 6.7 ACG-9: export

`audit.export` is a separate key from `audit.read`. Its only default holder is `builder_side_admin`, and a test asserts the owner holds neither. The export endpoint, format, delivery (non-bearer, AD-G-6 style) and the audit event for the export itself (ACG-INV-9, -10) are **DEFERRED** to the audit-API task (§11).

### 6.8 Still open in the Audit domain (not decided here)

| Item | Why open | How the schema keeps every answer possible |
|---|---|---|
| **AGX-10 ledger** | The PO must confirm the ledger reading. It is narrowed by §6.4: R6 is *not* superseded at the storage layer | Nothing to change if confirmed. If the PO requires physical deletion, that is a different, privileged path (AD-G-18) and a PO decision against ACG-8 and GC-46 |
| **AGX-11** — GC-22's "permanent, undeletable" support-session trail | Is it exempt from ACG-3/4? | One predicate in `audit_events_supersession_guard` (for example, refuse to supersede rows with `actor_type = 'support'`). No data-model change |
| **NI-9** — soft or hard audit "delete" | The mechanism is soft by construction | See J-1 |
| **ACG-INV-1** — the event taxonomy | Business events arrive with their phases | Categories are a CHECK. Extending it is one generated migration |
| **ACG-INV-12** — tamper evidence (hash chaining) | Not designed | Append-only plus supersession-as-rows is exactly the structure a hash chain needs, because corrections are chain members rather than holes |

## 7. Phase 0 defect found and fixed: direct partition access bypassed RLS

**Finding.** 0000 §7 enabled and forced RLS on the partitioned *parent* `audit_events` only. Its R1 lint excluded `audit_events_%` because "partitions inherit from parent". That holds for queries **through the parent**. It is false for queries that name a partition **directly**: each partition is its own relation, with row security disabled by default. The out-of-band `GRANT … ON ALL TABLES IN SCHEMA public TO crm_app` had also granted `SELECT, INSERT` on all 13 partitions.

**Verified on the live test database before the fix**, as `crm_app`:

| Probe | Result |
|---|---|
| `SELECT count(*) FROM audit_events WHERE …` as tenant B, row belongs to tenant A | 0 (parent policy works) |
| `SELECT count(*) FROM audit_events_2026_10 WHERE …` as tenant B | **1 — tenant A's row visible** |
| Same, with **no tenant context at all** | **1** |
| `INSERT INTO audit_events_2026_10 (tenant_id …)` with no context | **Succeeded (forged row)** |

**Fix (0004 §2, §6), two independent layers.**

- **(a)** Every partition gets the same `ENABLE` + `FORCE` + `tenant_isolation` policy. Queries through the parent are unaffected, because PostgreSQL applies only the parent's policy to them.
- **(b)** Every direct `crm_app` privilege on the partitions is revoked. Access through the parent needs privileges on the parent only.

After the fix, both probes fail with `permission denied`. The regression test is P1-ACG-R1b. The lint no longer excludes partitions (P1-C-1), and a grant check (P1-C-7) asserts `crm_app` holds nothing on any partition.

**Recommended follow-up (PO or maintainer):** the architecture note's §8/§10 lint text and the `schema-phase-0.sql` comment ("partitions inherit from parent") should be corrected. They were not edited here, because Phase 0's records are preserved as executed (compare 00 §14).
